# Tooling Discovery

An agent that does not know what it has will re-invent it badly. This handbook defines what is discovered, from where, in what precedence, and what an agent owes the next reader.

## The inventory

`status/TOOLING.md` (machine-readable twin: `status/tooling.json`) is generated by:

```bash
python3 scripts/discover_tooling.py           # refresh
python3 scripts/discover_tooling.py --check   # fail when stale — used by CI
```

It records, with real counts from the discovered environment:

| Section | Source |
|---|---|
| Global skills | `~/.claude/skills/**/SKILL.md`, grouped into android / ui-design / process / security / backend / media / other |
| Project skills | `.claude/skills/**/SKILL.md` (this repository's rules — these win) |
| Plugins | `~/.claude/plugins/installed_plugins.json` |
| Marketplaces | `~/.claude/plugins/known_marketplaces.json` |
| Slash commands | `~/.claude/commands/*.md` |
| MCP servers | `~/.claude.json` (user scope + per-project entries), `.mcp.json`, `.cursor/mcp.json`, `.claude/settings.json`, `.vscode/mcp.json` |
| Design skill library | `~/.claude/design-skill-library` (curation index + entry count) |
| Community index | whether `npx skills` is available |

Environment variables of MCP servers are listed **by name only**. A value never reaches the report, the log or the repository.

## Discovery levels and precedence

```
1. Project skills        .claude/skills/**        ← authoritative for this repo
2. Project MCP servers   .mcp.json                ← enabled via .claude/settings.json
3. Project subagents     .claude/agents/**
4. Global skills         ~/.claude/skills/**
5. Global plugins        ~/.claude/plugins/**     ← skills, subagents, hooks they ship
6. Global MCP servers    ~/.claude.json → mcpServers
7. User commands         ~/.claude/commands/**
8. Community skills      npx skills find/add      ← unvetted, owner confirmation required
```

Two rules follow from that order:

- **A project skill overrides a global skill** when both cover the same ground, because the project skill encodes this repository's constraints (German-first strings, no secrets in logs, `dr_` key format, one commit per task…).
- **A connected MCP server beats new code.** If the capability exists as a tool, call it. Reimplementing an existing tool is scope creep with a maintenance bill.

## How MCP servers actually get found

| Config | Scope | Picked up by |
|---|---|---|
| `~/.claude.json` → `mcpServers` | all projects | Claude Code automatically |
| `~/.claude.json` → `projects[<path>]` → `mcpServers` | one project | Claude Code automatically, in that directory only |
| `.mcp.json` in this repo | this repo, every session | Claude Code, auto-enabled by `enableAllProjectMcpServers` in `.claude/settings.json` |
| `.cursor/mcp.json`, `.vscode/mcp.json` | other editors | discovered and reported by the inventory, not used by Claude Code |

`.mcp.json.example` is the template. It contains no credentials — MCP secrets are referenced as environment variables, and `scripts/preflight-secrets.sh` blocks a commit containing a real one.

DroidRoute's own MCP federation (`docs/07-mcp-plugins.md`) is a separate, product-level feature: the app discovers the servers its agents use and bridges their tools over `POST /mcp/{id}`.

## What an agent owes the log

Record every tooling decision so the next reader does not have to reconstruct it:

```
skill-selection: mobile-android-design + droidroute-verification (impl/verify pair)
skill-substitution: security-audit -> android-intent-security (no generic security skill installed)
mcp-used: <server> for <capability>
skill-install-request: <owner/repo> — confirmed with owner before install
tooling-stale: regenerated status/TOOLING.md (env changed since last commit)
```

## When nothing fits

Order of escalation:

1. Look again with the domain grouping in `status/TOOLING.md` — the right skill is often already there under a name you would not have guessed.
2. Ask the `tooling-scout` subagent to search.
3. `npx skills find <query>` for the community index; preview with `--list` before installing.
4. Only then write the procedure yourself — and if it is reusable, add it as a project skill under `.claude/skills/<name>/SKILL.md` so it is not written twice.

## Staleness

The environment changes (a plugin gets installed, an MCP server is added). CI checks `--check`, and so should you before starting a long task: a stale inventory means an agent may skip a skill that exists. Regenerating it is one command and produces a commit whose diff explains itself.

## Adding a project skill

```
.claude/skills/<name>/SKILL.md
---
name: <name>
description: <what it does>. Use when <trigger>.
---
```

Then it appears in the inventory and in Claude Code's skill list for this repository. Keep it about **this project's rules** — general technique belongs in the global library or the community index, not here.
